## 3.1 Introduction to the Team Charter

An Agile Team Charter establishes a shared understanding of a team's purpose, working principles, responsibilities, and expectations. It helps create clarity about how work should be approached and what the team is trying to achieve.

For this portfolio, I developed a retrospective Agile Team Charter to demonstrate how these principles could be applied to a website development and maintenance context.

The charter focuses on communication, organisation, quality, responsibility, and continuous improvement.

## 3.2 Proposed Team Charter

| Element | Description |
|---|---|
| Purpose | To organise website-related work in a clear and structured way. |
| Main focus | Website maintenance, frontend development, image and asset integration, and quality review. |
| Shared goal | To support the development and maintenance of website pages that present information clearly and meet defined requirements. |
| Communication | Ensure that requirements, questions, and task expectations are communicated clearly. |
| Task organisation | Break larger activities into smaller tasks that can be understood and reviewed. |
| Quality expectations | Review work against relevant requirements before considering a task complete. |
| Responsibility | Take responsibility for assigned work and communicate when clarification is needed. |
| Continuous improvement | Reflect on completed work and identify what could be improved in future tasks. |

## 3.3 Definition of Done

The Definition of Done describes the conditions that should be met before a task is considered complete. I developed the following Definition of Done retrospectively to apply professional Agile standards to my internship context.

| Criterion | Explanation |
|---|---|
| Requirements understood | The purpose and expected outcome of the task are clear. |
| Work completed | The planned task has been carried out according to its requirements. |
| Relevant checks performed | Appropriate checks have been considered for the type of work completed. |
| Quality reviewed | The result has been reviewed against the agreed acceptance criteria. |
| Issues identified | Any known issues or incomplete items have been recorded for further attention. |
| Documentation updated | Relevant task notes or records have been updated where appropriate. |

The exact checks would depend on the task. For example, a website content change may require a different review from a change to frontend code.

# 4. User Stories and Tasks

## 4.1 Introduction to User Stories

User stories are used in Agile development to describe a requirement from the perspective of the person who needs or benefits from it. They help explain why a particular feature or activity matters instead of focusing only on the technical task.

A common format is:

**As a [type of user], I want [a goal], so that [a benefit].**

For this portfolio, the user stories below are proposed examples based on the website-related activity areas in my placement records. They demonstrate how those activities could be expressed as user needs.

They are not presented as confirmed requirements supplied by the placement organisation.

## 4.2 User Story 1: Website Maintenance

**User story**

As a website visitor, I want website information to be maintained and presented correctly so that I can access useful and up-to-date information.

**Proposed tasks**

- Identify the website content or page area that requires attention.
- Clarify the expected outcome of the maintenance activity.
- Review the relevant content or page elements.
- Make the required change, where authorised.
- Check the result against the task requirements.
- Record any outstanding issues.

**Acceptance criteria**

- The purpose of the maintenance task is clear.
- The intended change addresses the identified requirement.
- The relevant page content is reviewed after the change.
- Any known outstanding issues are recorded.

### Reflection on User Story 1 

**Situation:** Website maintenance is one of the activity areas documented in my placement records.

**Task:** I needed to demonstrate how a general maintenance activity could be expressed as a user need and broken into smaller tasks.

**Action:** I created a proposed user story focused on website visitors and listed tasks covering the identification, review, and checking of a maintenance requirement.

**Result:** The example shows how maintenance can be organised around a clear purpose rather than treated as an isolated technical activity.

**Reflection and learning:** I learned to consider maintenance from the visitor's perspective. In future projects, I would clarify the purpose of a maintenance task before starting and use clear acceptance criteria to help review the result.

## 4.3 User Story 2: Image and Asset Integration

**User story**

As a website visitor, I want images and visual assets to be displayed appropriately so that the website is easier to understand and navigate.

**Proposed tasks**

- Identify the visual assets required for the relevant page.
- Confirm that the assets are suitable for their intended purpose.
- Identify where the assets should appear.
- Integrate the assets into the relevant page, where required.
- Review the visual presentation of the page.
- Check for missing or incorrectly displayed assets.

**Acceptance criteria**

- The intended assets are identified.
- Assets are placed in the appropriate page areas.
- The page is reviewed for missing or incorrectly displayed images.
- Any identified issues are recorded for correction.

### Reflection on User Story 2 

**Situation:** Image and asset integration is one of the activity areas recorded during my placement.

**Task:** I needed to demonstrate how an asset-related activity could be organised around the needs of a website visitor.

**Action:** I created a proposed user story and broke the work into tasks covering asset identification, placement, integration, and review.

**Result:** The example shows how visual asset work can be planned and checked against the intended page presentation.

**Reflection and learning:** I learned that images are not only decorative elements; they can also support the communication and presentation of information. In future projects, I would check that assets are suitable for their purpose and review how they appear within the page.

## 4.4 User Story 3: User Interface Presentation

**User story**

As a website visitor, I want page elements to be organised clearly so that I can understand the information presented and use the website more easily.

**Proposed tasks**

- Identify the relevant page or interface area.
- Review the purpose of the interface elements.
- Identify the expected arrangement of content and visual elements.
- Implement the required interface changes, where applicable.
- Review the page presentation against the requirements.
- Record any issues that still need attention.

**Acceptance criteria**

- The intended interface requirements are understood.
- Page elements are arranged according to the defined requirements.
- The page is reviewed for presentation issues.
- Any identified issues are documented.

### Reflection on User Story 3 

**Situation:** User interface implementation and frontend development are activity areas covered by my placement records.

**Task:** I needed to show how interface work could be described in terms of the experience it provides to a website visitor.

**Action:** I developed a proposed user story and identified tasks for understanding the interface requirements, planning changes, and reviewing the page presentation.

**Result:** The example demonstrates how interface work can be linked to a user's needs and reviewed against defined requirements.

**Reflection and learning:** I learned that a page can contain the correct information but still be difficult to use if its elements are not organised clearly. In future work, I would consider the intended user experience when reviewing interface requirements.

## 4.5 User Story 4: Website Quality Assurance

**User story**

As a website user, I want relevant pages and features to be checked so that problems can be identified and addressed.

**Proposed tasks**

- Identify the page, feature, or area that requires review.
- Establish what needs to be checked.
- Perform appropriate checks based on the task requirements.
- Record any issues identified.
- Correct issues where authorised and within the task scope.
- Review the relevant area again after corrections, where applicable.

**Acceptance criteria**

- The area to be checked is identified.
- Relevant checks are performed.
- Identified issues are documented.
- Any required corrections are reviewed against the original requirements.

### Reflection on User Story 4 

**Situation:** Website quality assurance and application testing and debugging are activity areas documented in my placement records.

**Task:** I needed to demonstrate how quality-related work could be expressed as a requirement with clear tasks and acceptance criteria.

**Action:** I created a proposed user story focused on checking website pages or features, recording issues, and reviewing corrections where applicable.

**Result:** The example provides a structured way to consider how quality checks can support the identification and resolution of problems.

**Reflection and learning:** I learned that creating or changing a page is different from checking whether it meets its requirements. In future projects, I would identify the checks needed for each task and document issues clearly so they can be followed up.

## 4.6 Overall Reflection on User Stories and Tasks — STAR

**Situation:** My placement records contained broad website-related activity headings rather than detailed user requirements.

**Task:** I needed to demonstrate how those activity areas could be translated into proposed user stories, tasks, and acceptance criteria.

**Action:** I created four proposed user stories covering maintenance, asset integration, interface presentation, and quality assurance. I broke each story into smaller tasks and identified criteria that could be used to review the expected outcome.

**Result:** The examples demonstrate how general activities can be organised around user needs and clearer expectations.

**Reflection and learning:** This process helped me move from thinking only about the task itself to considering the reason for the task and the value it could provide to a user. In future projects, I can use user stories to explain requirements and acceptance criteria to help determine whether the intended outcome has been achieved.

# 5. Product Backlog

## 5.1 Introduction to the Product Backlog

A Product Backlog is an organised list of work that may be required for a product or project. It can include features, improvements, maintenance activities, and quality-related tasks.

The backlog helps make work visible and provides a basis for prioritisation. It can be updated as requirements become clearer or as new needs are identified.

For this portfolio, I developed a proposed Product Backlog using the website-related activity areas documented in my placement records. The priorities are suggested for this learning exercise and are not confirmed priorities from the placement organisation.

## 5.2 Proposed Product Backlog

| ID | Backlog item | Description | Suggested priority | Reason for priority |
|---|---|---|---|---|
| PB01 | Review website maintenance needs | Identify the page or content area requiring attention. | High | Clear requirements help establish the work that needs to be completed. |
| PB02 | Review website content | Check relevant content against the task requirements. | High | Correct and clear information supports the visitor's experience. |
| PB03 | Identify required visual assets | Determine which images or assets are needed for a page. | Medium | Asset requirements should be understood before integration. |
| PB04 | Integrate website assets | Place the required assets in the appropriate page areas. | Medium | Visual elements contribute to page presentation. |
| PB05 | Review user interface requirements | Identify how page elements should be presented. | High | Understanding the intended interface helps guide implementation. |
| PB06 | Implement interface changes | Carry out proposed interface updates according to requirements. | Medium | Implementation follows the identification of the required changes. |
| PB07 | Develop or update web pages | Address relevant web page development requirements. | High | Page development supports the structure and content of the website. |
| PB08 | Maintain frontend code | Review and maintain relevant frontend code as required. | Medium | Maintaining code supports future changes and ongoing development. |
| PB09 | Perform relevant quality checks | Review pages or features against defined requirements. | High | Quality checks help identify issues before work is accepted. |
| PB10 | Record issues and improvements | Document findings and areas requiring further attention. | Medium | Documentation supports follow-up and continuous improvement. |

## 5.3 Prioritisation Approach

The proposed priorities are based on the relationship between the activities and their potential contribution to website quality.

High-priority items focus on understanding requirements, reviewing content, clarifying the interface, developing relevant pages, and checking quality. These activities help establish what needs to be done and whether the outcome meets its intended purpose.

Medium-priority items focus on specific implementation and maintenance activities that can be planned according to the requirements of the work.

In an actual project, the order would depend on factors such as stakeholder requirements, dependencies between tasks, available time, technical constraints, and the urgency of identified issues.

## 5.4 Reflection on the Product Backlog 

**Situation:** The website-related activity areas in my placement records cover several types of work that could be organised into a backlog.

**Task:** I needed to demonstrate how these activities could be listed and prioritised in an organised way.

**Action:** I developed a proposed Product Backlog containing ten items, descriptions, suggested priorities, and reasons for those priorities.

**Result:** The backlog provides an example of how website-related work can be made visible and arranged according to its purpose and potential importance.

**Reflection and learning:** This helped me understand that not all tasks need to be approached at the same time. Prioritisation should consider requirements, dependencies, and value rather than simply choosing the easiest task. In future projects, I would clarify the requirements and discuss priorities before deciding the order of work.

# 6. Sprint Backlog

## 6.1 Introduction to the Sprint Backlog

A Sprint Backlog identifies the work selected for a sprint and explains how that work contributes to a defined goal. It helps a team organise tasks within a limited period and review progress towards the goal.

I developed this Sprint Backlog retrospectively to demonstrate my understanding of how to plan and time-box a website-related goal. The example below is a proposed planning exercise, not a record of a confirmed sprint at my placement.

## 6.2 Proposed Sprint Goal

**Sprint goal:** Plan and review the integration of visual assets into a website page according to defined requirements.

This goal was selected because image and asset integration is one of the activity areas documented in my placement records.

## 6.3 Proposed Sprint Backlog

| Task ID | Task | Expected outcome | Completion check |
|---|---|---|---|
| SB01 | Clarify the page requirements | A clear understanding of the intended page outcome | Requirements are documented in the task plan. |
| SB02 | Identify the required assets | A list of assets needed for the page | Required assets are identified. |
| SB03 | Plan the asset placement | A clear plan for where the assets should appear | Planned placement matches the page requirements. |
| SB04 | Plan the integration work | A sequence of implementation steps | The steps are clear and manageable. |
| SB05 | Review the page presentation | A review of how the assets should appear in context | The page can be checked against the requirements. |
| SB06 | Record issues and follow-up work | A list of identified issues or remaining tasks | Outstanding items are documented. |

## 6.4 Proposed Sprint Review Criteria

At the end of the proposed sprint, the work could be reviewed using the following questions:

- Were the requirements understood?
- Were the necessary assets identified?
- Was the planned placement consistent with the intended page presentation?
- Were the appropriate review checks identified?
- Were any outstanding issues documented?
- What could be improved in the next development cycle?

These questions would help determine whether the planned work met its goal and whether additional tasks should be added to the Product Backlog.

## 6.5 Reflection on the Sprint Backlog 

**Situation:** I needed to demonstrate how a broad website-related goal could be organised into manageable pieces of work.

**Task:** My task was to create a proposed Sprint Backlog showing a sprint goal, individual tasks, expected outcomes, and completion checks.

**Action:** I selected asset integration as the example goal and divided the proposed work into six tasks covering requirements, asset identification, placement planning, integration planning, review, and documentation.

**Result:** The Sprint Backlog demonstrates how a larger goal can be divided into smaller steps and how each step can have an expected outcome.

**Reflection and learning:** This helped me understand that planning is not only about listing tasks. It also involves identifying how progress and outcomes will be reviewed. In future projects, I would use a clear goal, organise tasks according to their dependencies, and check whether the planned outcome has been achieved.
