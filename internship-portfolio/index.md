# 4. User Stories and Tasks

## 4.1 Introduction

User stories describe a requirement from the perspective of the person who needs or benefits from a system or feature. They help explain what is required and why it matters.

The following user stories are retrospective examples based on the types of website activities recorded during my placement. They are not claimed to be actual user stories issued by the organisation.

## 4.2 User Story 1: Updating Website Images

**User story**

As a website visitor, I want website pages to display relevant images so that I can understand the products or information being presented.

**Related tasks**

- Identify the page or content area that requires an image update.
- Confirm which image or asset is intended for use.
- Add or update the image according to the task instructions.
- Review how the image appears on the relevant page.

**Acceptance criteria**

- The intended image is used.
- The image appears in the correct content area.
- The image is displayed clearly.
- The image does not create an obvious presentation problem.

**Reflection**

This example helped me consider how images contribute to the presentation of website content. An image should not simply be added without checking whether it is relevant and displayed appropriately.

## 4.3 User Story 2: Maintaining Existing Website Content

**User story**

As a website visitor, I want website information to be presented clearly so that I can find and understand the information I need.

**Related tasks**

- Review the assigned website content.
- Identify the specific area that needs attention.
- Make only the changes required by the task.
- Review the result to ensure the content remains understandable.

**Acceptance criteria**

- The assigned change has been completed.
- Unrelated content has not been changed unnecessarily.
- The page remains readable.
- Any obvious issues identified during review are addressed or reported.

**Reflection**

This example demonstrates why website maintenance requires care. When working on an existing website, it is important to understand the requested change and avoid making unrelated changes.

## 4.4 User Story 3: Improving Image Presentation

**User story**

As a website visitor, I want images to be presented consistently so that the website is easier to view and navigate.

**Related tasks**

- Review the presentation of the relevant images.
- Compare the result with the task instructions or existing page layout.
- Check whether images are positioned appropriately.
- Report any presentation issues that cannot be resolved within the assigned task.

**Acceptance criteria**

- Images are presented in the intended area.
- Images are suitable for the relevant content.
- The presentation is checked after the change.
- Any unresolved problems are communicated to the responsible person.

**Reflection**

This user story made me think about the relationship between visual presentation and usability. A website can contain useful information, but poor presentation can make that information harder to understand.

## 4.5 User Story 4: Reviewing Completed Website Changes

**User story**

As the person responsible for maintaining website quality, I want completed changes to be reviewed so that obvious problems can be identified before the work is considered finished.

**Related tasks**

- Review the changed page or content area.
- Check whether the result matches the task requirements.
- Identify visible problems.
- Record or report problems that need further attention.

**Acceptance criteria**

- The completed change is reviewed.
- The review considers the task requirements.
- Identified issues are recorded or communicated.
- The task is not assumed to be correct without checking the result.

**Reflection**

This example shows why reviewing completed work is important. Completing a task is only one part of the process. Checking the result helps identify problems that might otherwise be overlooked.

## 4.6 Overall Reflection on User Stories

Writing these examples helped me understand how technical activities can be connected to the needs of website visitors and the people responsible for maintaining a website.

User stories also make it easier to explain why a task is necessary. Instead of only saying that an image must be updated, the story explains how the change can support the visitor's experience.

In future projects, I would like to become more confident in writing clear requirements and identifying acceptance criteria before starting work.

# 6. Sprint Backlog

## 6.1 Introduction

A sprint backlog is a selection of work intended to be completed during a sprint, together with a goal and the tasks needed to achieve it.

The sprint below is a proposed example for this portfolio. It uses a website image or content update as a practical scenario based on the types of activities recorded during my placement. It is not a claim that this exact sprint took place at the organisation.

## 6.2 Proposed Sprint Goal

**Sprint goal:** Complete an assigned website content or image update and review the result against the task requirements.

The goal is to focus on one manageable piece of work, from understanding the requirement to checking the result.

## 6.3 Proposed Sprint Backlog

| ID | Task | Expected outcome |
|---|---|---|
| SB01 | Review the task instructions | Understand the requested change |
| SB02 | Identify the relevant page or content area | Know where the change is required |
| SB03 | Confirm the intended content or image | Use the correct asset or information |
| SB04 | Complete the assigned update | Apply the required change |
| SB05 | Review the updated page | Check the presentation of the result |
| SB06 | Identify and report any issues | Make sure unresolved problems are communicated |
| SB07 | Reflect on the completed task | Identify learning points and possible improvements |

These are proposed tasks for demonstrating sprint planning. They should not be interpreted as a record that I personally completed every item in this exact sequence.

## 6.4 Suggested Workflow

**Step 1: Understand**

Read the instructions and identify the expected result.

**Step 2: Plan**

Break the work into smaller tasks and identify what is needed.

**Step 3: Complete the assigned change**

Carry out the task according to the instructions and any relevant workplace procedures.

**Step 4: Review**

Check the result and compare it with the requirements.

**Step 5: Reflect**

Record what went well, what was difficult, and what could be improved next time.

## 6.5 Suggested Review Questions

At the end of this proposed sprint, the following questions could be used:

- Was the requested change completed?
- Does the result match the task requirements?
- Were any problems identified during the review?
- Was anything unclear during the task?
- What could be done more efficiently next time?

## 6.6 Reflection on the Sprint Backlog

Creating a sprint backlog helped me understand how a goal can be broken into smaller, more manageable tasks.

It also helped me see why reviewing the result should be included in the plan rather than treated as an optional step at the end.

I would like to improve my ability to estimate the work required for a task and keep better records of progress. This would make it easier to identify delays and understand what still needs to be completed.
